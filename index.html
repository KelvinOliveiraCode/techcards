Decisões técnicas

Stack e as razões de cada escolha

Nenhuma tecnologia foi adotada por preferência de moda. As seis decisões abaixo explicam o desenho do aplicativo.

Java 21 LTS
Suporte longo reduz o risco de reescrita e abre espaço para recursos estáveis: records, sealed e switch com pattern matching deixam o modelo de domínio mais explícito. É também a linguagem pedida na disciplina.
JavaFX 21 UI
Interface desktop nativa, sem browser embutido. O design system é escrito em CSS, então a paleta vive em um arquivo — e não espalhada por controllers.
SQLite sqlite-jdbc
Arquivo único, transacional e sem servidor. Isso elimina conta, login, sincronização e migração de esquema — o banco cabe em um .db que vai para o zip, para o backup e para o versionamento.
Maven + shade
Build reprodutível e declarativo. O shade plugin resolve as dependências em um único jar executável, que é o pré-requisito do empacotamento nativo.
jpackage app-image
Gera o pacote com o JRE 21 embarcado. O destinatário não instala Java, e o aplicativo abre sem rede — o que era requisito do projeto.
JUnit 5 46 testes
Cobrem DAO, seed, CRUD, estudo e métricas. Rodam sem subir interface porque a regra de negócio está isolada na camada de Service — a separação existe para tornar isso possível.

Consequências práticas

Nenhuma camada depende de outra além da direção da regra: a UI conhece os Services, os Services conhecem o DAO, e o DAO conhece o SQL.

  • Testes de regra de negócio rodam sem interface gráfica
  • Trocar o SQLite por outro banco mexe só no DAO
  • A seed entra por seed.json, sem SQL hardcoded
  • O backup é copiar um arquivo, porque não há servidor

Por que SQLite

O banco é um arquivo local em %USERPROFILE%/.techcards/. Sem servidor, sem login, sem nuvem. O aplicativo funciona sem rede e o histórico permanece na máquina do usuário.

Por que registrar histórico

O histórico existe para apontar o que foi errado de forma repetida. O dashboard já apresenta esse ranking. O que ainda falta é usá-lo para montar a fila de estudo automaticamente.

Formas de estudo: o que existe e o que falta

A separação abaixo é deliberada. O que já está no código aparece como entregue; o que não está aparece como pendência, sem dressing.

Entregue

Card clássico

Frente, verso, virada 3D, acerto, erro, som e streak. Fila embaralhada por aleatório ou por dificuldade.

Entregue

Ranking de erros

O dashboard ranca os 5 cards mais errados. Falta convertê-los em fila de estudo, e não apenas em número numa tela.

Pendente

Modo prova

Cronometrado, sem revelação antecipada, resultado ao fim. É o formato que a avaliação real exige.

Pendente

Revisão espaçada

Hoje o agendamento é manual. Um algoritmo equivalente ao SM-2 é a lacuna mais relevante do produto.

Pendente

Busca e filtro

Não há busca nos cards de um deck. Em 90 itens isso já é limitação de uso, não detalhe de implementação.

Pendente

Importar PDF

O material do professor entra como deck novo. Hoje só é possível cadastrar card por card.

Ambição · MCP

O banco local como protocolo

Um Model Context Protocol sobre o banco de estudos, para que a mesma superfície que um agente usa para automatizar seja a mesma usada para estudar.

Operações previstas para o agente

listar decks criar cards registrar sessão consultar desempenho gerar quiz por tema exportar histórico

Exemplo concreto: solicitar “monte um quiz de deadlock a partir dos meus erros”. O agente lê o histórico, monta a sessão e grava o resultado de volta no mesmo banco, onde a interface já mostra tudo.

Para o usuário

consultar os próprios números automatizar backup gerar material novo

A ideia não é levar dados para fora. É o oposto: o SQLite local deixa de ser apenas um arquivo de armazenamento e passa a ser uma interface programável, sem nuvem e sem conta.

Relação com o curso. Construir um servidor MCP exige projeto, protocolo, tratamento de erro e documentação — competências avaliadas nas mesmas disciplinas que o aplicativo estuda. O software deixa de ser o produto final e passa a ser o campo de treino.
